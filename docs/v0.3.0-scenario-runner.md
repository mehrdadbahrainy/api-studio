## Scope

A local, **script-free** scenario builder that chains saved requests, captures values from
responses, uses them only in subsequent requests and checks response assertions.

## Engine contract (Phase 1)

- A scenario references **saved request IDs**. It cannot accidentally send an arbitrary unsaved HTTP request.
- Up to 20 ordered steps, each with up to 12 assertions and 8 extractions.
- Assertion kinds: status equals, JSON field equals, JSON exists, header contains, duration below.
- Extraction sources: restricted, non-evaluating JSON property path such as $.token or $.orders[0].id, response header or status.
- Runtime variables are temporary in-memory values that override selected Environment
  variables for later steps. They are not written into Workspace, History, step results
  or reports. A failed step cannot publish partial extraction results.
- The runner uses the existing prepareRequest validation before HTTP I/O, and a
  supplied sender (the existing Tauri/browser executeRequest used by the GUI).
  Missing variables fail **before** a request is sent.
- No arbitrary JavaScript, eval, Postman scripts or untrusted command execution.
- Scenario results contain only counts, step IDs, fixed safe errors, pass/fail flags
  and durations. Raw response bodies, headers, URLs and extracted variable values
  are not present. The HTTP sender is responsible for not logging credentials.
- Default status success is 2xx/3xx if no explicit status assertion exists.
  An explicit expected 4xx status can pass when it is asserted.
- Cancellation uses AbortSignal, stops further requests, and preserves saved data.
  Stop-on-failure can be turned off only in the explicit scenario definition.

## Example definition used for tests

The same flow can be built through the new Scenario Builder on the development branch. This sequence is also a **test fixture**, not a separate public import format:

1. POST http://localhost:3000/auth/login, assert 200, extract $.token as secret token.
2. POST http://localhost:3000/orders, use Bearer {{token}}, assert 201,
   extract $.id as orderId.
3. GET http://localhost:3000/orders/{{orderId}}, assert 200, state placed
   and header X-Test contains ok.
4. PATCH http://localhost:3000/orders/{{orderId}}, assert 200 and state shipped.

Expected after **four real successful responses**: 4 Passed / 0 Failed.
A synthetic or mock unit test alone does not prove native desktop functionality.

## Scenario Builder workflow (development branch)

1. Save the HTTP requests you want to test in a Collection.
2. Choose the **Scenarios** sidebar tab and **Create scenario**. Name the scenario,
   choose ordered saved Request steps and set **Stop on first failure** when appropriate.
3. For each step, add **Assertions** for status, JSON fields, headers and duration,
   or an **Extraction** such as JSON body `$.token` as variable `token`.
   Later requests can use `{{token}}` in their Bearer Auth, URL, headers or body.
4. Click **Save scenario**. The definition is stored in the same Windows-protected
   or password-protected Workspace used for Collections; old v1 backups remain readable.
5. Click **Run scenario** and explicitly confirm network execution. No request is
   sent on Create, Add Step, Edit, Save or validation alone.
6. Inspect the counts and per-step assertions. **Cancel run** stops subsequent requests.
   Runtime response values, captured tokens and result bodies are not saved.

**Safety:** Use only a test server/Environment you control. POST/PATCH/DELETE and
even some GET endpoints can change remote state. A manual Run confirmation is not
a substitute for strict target allowlists and per-client authorization in the future
MCP Server (#28). Workspace exports are unencrypted; an assertion's manually
entered expected literal may itself be sensitive, so do not embed credentials
or private response values into Scenario definitions.

**Scope:** the graphical builder intentionally uses simple form fields, not
arbitrary JavaScript. The JSON equals editor interprets true, false, null
and numeric literals as typed JSON values; other entries remain strings.

## Release and QA restrictions

- Stable v0.2.2 remains unchanged until a separately verified v0.3.0 release is created.
- Do not close [#9](https://github.com/mehrdadbahrainy/api-studio/issues/9) or
  [#20](https://github.com/mehrdadbahrainy/api-studio/issues/20) because unit tests pass.

  interactive QA still require independent acceptance.

  reuse the *same* scenario model and runner semantics, but are not in v0.3.0.

  MSI acceptance and checksum-matched immutable release installers.
